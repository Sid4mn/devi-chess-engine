# v0.5.1 — Re-checking the Two-Phase Speedup

**v0.5.1** | June 2026 | Apple M1 Pro (8P + 2E)

> First correction to v0.5.0. I found a sign bug in the search and re-ran the two-phase benchmark - the 1.55x didn't survive. This release is just the bug fix; the scheduler is left untouched so the change is clean to attribute.

## Why this exists

Before pitching v0.5.0 I went back to re-run the benchmark and the headline number fell apart. So this is a correctness release: the search fix plus the fault-tolerance rework, and nothing else. The scheduler's QoS policy is unchanged from v0.5 - the E-pool is still on `QOS_CLASS_BACKGROUND`, `should_use_two_phase` is still in place. (The only edit to the scheduler file is thread-builder plumbing - thread names, stack size, error propagation - not routing or QoS.) So any change in the numbers is the bug fix, not new tuning.

## The bug

The root search negated the child score like negamax (`-alphabeta(...)`), but the eval is absolute / white-relative, not side-to-move-relative. So the alpha bound handed from phase 1 to phase 2 was unsound - it pruned subtrees it had no business pruning. That over-pruning is what made the E-core phase look fast. The v0.5 writeup's "key insight" (E-cores prune hard with the phase-1 bound) was describing the bug.

Fix (`690df81`): `root_move_score` makes the move and searches the child with the correct maximizing flag - no negation - flipping sign only for Black. Mate scores are distance-aware (`MATE - ply`). Ties resolve first-max so serial and parallel agree. The cross-phase alpha handoff is gone; every root move is searched full-window.

## What I measured

Same setup as v0.5: starting / Kiwipete / Position4, probe depths 1-3, ratios 0.5-0.8, depth 6, 10 runs, median. Scheduler unchanged. The Kiwipete baseline is noisy on this machine (~6% std dev when cool, ~12% hot), so I ran the whole sweep three times - hot, cooled, cold. The conclusion is identical in all three.

## Results — Kiwipete, depth 6

Baseline (10-thread work-stealing) lands at ~7.1s across the three runs. Two-phase against it:

| config | speedup (cold run) | range across 3 runs |
|--------|--------------------|---------------------|
| ratio 0.5, probe 1 | 1.02x | 1.01-1.10x → tie |
| ratio 0.6, probe 1 | 0.87x | 0.84-0.89x |
| ratio 0.6, probe 2 | 0.92x | 0.90-0.92x |
| ratio 0.7, probe 1 | 1.01x | 0.94-1.03x → tie |
| **ratio 0.8, probe 1  (v0.5's shipped config)** | **0.27x** | **0.24-0.27x** |

![Two-phase speedup vs heavy ratio](figures/speedup_vs_ratio.png)

The whole sweep in one line: every position hugs baseline parity while the safety abort keeps work on the P-cores, then drops off a cliff the moment a ratio is loose enough to ship moves to the E-cores - starting at 0.7, Kiwipete at 0.8.

- **The 1.55x is gone.** Best case, two-phase *ties* the baseline (ratio 0.5). It never wins.
- **The shipped flagship config collapses to ~0.26x** - ~4.4s of phase 1, then ~22-25s of phase 2, because with the bound fixed the 10 "light" moves now get searched full-window on `BACKGROUND`-throttled E-cores. The 1.55x was the bug pruning that work away.
- Probe depth 3 just adds ~0.6s of probe overhead for no benefit.
- The starting-position ratio-0.7 "disaster" from v0.5 is still here (down to ~0.05x, wildly variable) - same root cause.

What the phase breakdown makes obvious: at ratios 0.5-0.7 the light-overflow abort (`light_threshold=0.3`) fires and every move runs on the P-cores - light_count is 0, there is no phase 2, so the "tie" is just the baseline with a probe tax. Ratio 0.8 is the only Kiwipete config that actually peels moves off to the E-cores, and it's the one that craters. The config v0.5 shipped as the flagship is precisely the one that slips past its own safety valve.

Raw data: `benchmarks/v0.5.1/two_phase_benchmark_run{1,2,3}.csv` (hot / cooled / cold). Figures regenerated by `scripts/analyze_two_phase.py` into `releases/v0.5.1/figures/`.

## Fault tolerance

Also in this release (`b3d9510`): fault recovery reworked from a global-counter whole-search retry to per-move `catch_unwind` isolation, so one panicked root move no longer discards the whole parallel search. Fault-overhead numbers are tracked in `benchmarks/fault_overhead.csv`.

## Takeaways

1. The v0.5 1.55x was a measurement artifact of a sign bug, not a real speedup.
2. With correct search, two-phase never productively uses the E-cores: it either ties the baseline (safety abort runs everything on P-cores) or craters (it dispatches light moves to the throttled E-cores).
3. The ~22-25s phase-2 blowup points straight at the E-cores / QoS - that's the next thing to dig into.
4. Baseline variance is ~6% (cool) to ~12% (hot); the result holds across all three runs.

## Reproduction

```bash
cargo build --release
./target/release/devi --two-phase-benchmark --depth 6 --runs 10 --csv-output benchmarks/v0.5.1/two_phase_benchmark_run3.csv
```
